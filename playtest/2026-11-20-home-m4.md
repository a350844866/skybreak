### e2e 用例（`npm run e2e`：本机 2 个 worker 约 3.5 分钟，CI 设置下 1 个 worker 约 5 分钟）

| 用例 | 证明什么 |
|---|---|
| 完整一局（960×540） | • 五个阶段依次走完，5 次闪电全部是有效反应<br>• 游戏报告的反应时间不低于"闪电帧时间戳 → 点击"的真实间隔，最多比它高出测试工具自身的延迟（+100 ms 以内）。**画面晚出的延迟这个检查看不到**，见 §3.1<br>• 无人机：只有在点击晚于飞走时才允许一次 miss，点中活着的无人机不允许 miss；每次命中的倍率逐个符合连击规则<br>• 结算卡显示四项评分和"First run of the day!"<br>• 输入缩写后，主屏 Top 3 和副屏排行榜都出现该缩写；副屏在对局中显示 LIVE<br>• 各关卡 JS 耗时 p95 < 8 ms（留了 CI 余量，真机 ≤ 0.6 ms）；主屏和副屏都是 0 条报错 |
| 彗星（640×360） | 窗口小到 SwiftShader 跟得上，光标跟随时锁定帧占比 > 60%，结算卡最长锁定 > 0.5 s |
| 抢跑与预判 | • 闪电出现前的 2 次点击都判 false-start<br>• 第 2 次闪电后 10 ms 的合成点击判 false-start（不会被记成 10 ms 的反应）<br>• 所有有效反应 ≥ 100 ms，结算卡显示"3 too early" |
| 放弃的一局 | • 全程不操作：只有 1 次闪电，0 命中，无人机全部飞走<br>• 在结算页停 10 s 后误点一次：成绩不丢，不跳页，空闲计时从这次点击重新算<br>• 点击后 23–28 s 回到 ATTRACT，并以 AAA 保存 |
| 中途改窗口尺寸 | • 改尺寸前出现的无人机，会画在新尺寸下重新投影的位置；按旧坐标会画到的位置没有无人机（截图检测青色像素）<br>• 通过运营面板暂停 → 改尺寸 → 关面板后，点击新位置能命中 |
| 运营面板暂停 | 面板打开 3.5 s：不出闪电、阶段不变、阶段计时条消耗 < 10%（如果时钟没冻结会是 23%）；关闭后 3.5 s 内出闪电 |
| 运营工具 | 错误 PIN 被拒；诊断文本格式正确；导出 CSV（文件名、表头、数据）；清空当天；改 PIN 后旧 PIN 失效、新 PIN 可用 |
| 离线 | Service Worker 接管后断网：主屏和副屏都确认由 Service Worker 返回（`fromServiceWorker`），都能加载，并能开局 |

## 3. 给 MBP Claude / Junie 的发现

### 3.1 材质首次使用时主线程卡一下（低优先，建议放进 Junie 任务 #1 或 #2）

| 环境 | 首次闪电 | 首次彗星 | 之后 |
|---|---|---|---|
| SwiftShader 720p（3 次） | 91–135 ms 的帧 | 25–52 ms | < 1 ms |
| SwiftShader 1080p（1 次） | 261 ms | 117 ms | < 1 ms |
| Apple M2 Pro 真 GPU（[`2026-11-20-mbp.md`](https://github.com/a350844866/skybreak/blob/playtest-mbp/playtest/2026-11-20-mbp.md)） | 关卡内 JS max 2.3 ms，0 帧 > 25 ms | 同左 | — |

- Chrome trace 显示：GPU 进程每帧都在 `GLContextEGL::MakeCurrent` 上花 60–90 ms（SwiftShader 软件渲染很慢）。材质第一次渲染时，渲染线程要和 GPU 进程同步，等待时间就是整条积压的渲染队列，所以卡顿和分辨率成正比，而且每种材质只发生一次
- 这一帧有时正好落在闪电那一帧，有时晚几百毫秒。落在闪电帧时，画面晚出，但反应计时已经开始，**页面加载后第一位玩家的第一次反应就会被多算这段时间**。e2e 的反应时间检查是从事件发出时刻算的，看不到这段画面延迟，所以抢跑用例特意避开了第 1 次闪电
- > 推断：Windows 核显上 ANGLE 走 D3D11，HLSL 编译本身就慢，展位真机可能出现几十毫秒的首帧卡顿。未实测
- 建议修法：加载阶段或 ATTRACT 期间把所有效果组临时设为可见，调一次 `renderer.compile(scene, camera)`（或者渲染一帧玩家看不到的预热帧），让材质在任何关卡开始前就编译完成
- 验收：
  - SwiftShader 下重新开页面，各关卡首帧 JS < 50 ms。可以用 `tests/e2e/support.ts` 的 `frameSummary` 看 `workMax`。修好后建议 Junie 在 e2e 里加一条"各关卡 `workMax` < 50 ms"的断言；修好前这个指标时有时无，没法写成稳定的已知失败用例
  - 用 `bot_mbp.py` 看第一次闪电的帧

### 3.4 读 e2e 数据时注意

- SwiftShader 在 1080p 只有约 5 fps，机器人追彗星追的是约 100 px 前的旧位置，所以 e2e 只检查"能锁定"，不检查锁定率
