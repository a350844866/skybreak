## 2. 方法

- 打开 `http://localhost:5201/?hook`，点 `#panel .cta` 开局。注意 CTA 有无限的 pulse 动画，Playwright 的 `click()` 永远等不到元素"稳定"，所以改为按 bounding box 中心直接 `mouse.click`
- 机器人策略按任务书执行：
  - 闪电：收到 `flash` 后随机等 200–300 ms 再点
  - 无人机：收到 `drone-spawn` 后分 6 步、每步 35 ms 把鼠标移过去再点
  - 彗星：每 15 ms 读最新的 `comet` 事件，把鼠标移到它的 point
  - RESULTS 之后不做任何输入，等 25 s 空闲回到 ATTRACT 再开下一局，3 组都这样做
- 事件读取：通过 `__skybreakFx` 的 setter 在每个事件 push 时复制一份到机器人自己的队列，每次 poll 时清空。这样游戏自己裁剪数组（超过 4000 条时砍掉前 2000 条）也不会漏读或重复读，游戏逻辑不受影响
- 帧计时：注入任务书给的 rAF 包装脚本，记录 `[ts, 帧间隔, JS+提交耗时, 阶段, 渲染倍率]`，同一帧的多个 rAF 回调合并为一条。**JS 耗时只包含 rAF 回调内部**，不含事件处理、样式布局、GPU 执行
- 启动参数：`--enable-precise-memory-info`（不加的话 `usedJSHeapSize` 会被分桶、并缓存约 20 分钟，耐久曲线会假平）、`--mute-audio`（合成器照常运行，只是扬声器静音）、`--window-position=0,0`（让窗口落在内建屏上）。**没有任何 swiftshader / GPU 相关参数**
- 耐久测试每次回到 ATTRACT 时依次记录：`performance.memory.usedJSHeapSize`（原始值）→ 通过 CDP `HeapProfiler.collectGarbage` 强制 GC → 再读一次 → CDP `Performance.getMetrics`（Nodes / JSEventListeners / Documents）
- 首局卡顿的根因用 Chrome trace 定位，见 §4.2

### 3.4 机器人自身的偏差（读数据时注意）

- **Flick 读数随刷新率变化**：120 Hz 下约 256 ms，60 Hz 下约 306 ms。原因是 CDP 的 `Input.dispatchMouseEvent` 会等渲染端处理完 mousemove 才返回，而 mousemove 是按帧对齐的，6 步移动每步多等约半帧。这是测量工具的特性，不是游戏变慢；120 Hz 下每 20 s 能打 77 架，60 Hz 下 63 架
- **Reaction 链路校验**：机器人"收到 flash 后等 200–300 ms"，游戏测得 217–302 ms，均值 253 ms。说明从闪电到点击的计时链路额外开销只有约 3–5 ms，测量准确

## 4. 发现的问题

### 4.1 彗星段：人类跟不上（严重，体验层面）

按 `src/game/stages/comet.ts` 的轨迹公式，用 400 条随机轨迹、每条 20 s、10 ms 步长模拟（1080p 下）：

| 指标 | 数值 |
|---|---|
| halo 半径 | 46 px（`min(46, 0.075 × 短边)`） |
| 彗星速度 | p50 **573 px/s**，p90 **1,079 px/s**，p95 1,230 px/s，max 1,622 px/s |
| 瞬时反向 | 每 1.5–3 s 一次，平均 2.25 s，20 s 内约 9 次。速度方向**瞬间**掉头，没有减速过渡 |
| 3 s 锁定奖励 | 需要连续 3 s 不出圈；平均 2.25 s 一次反向，所以几乎每个 3 s 窗口里都会碰上至少一次掉头 |

> 推断（示意，非实测）：人手追踪的等效延迟按 150–250 ms 算，p50 速度下这段时间彗星已经移动 86–143 px，是 halo 半径的 2–3 倍；一次瞬时反向后，人与彗星的相对偏移在 200 ms 内约达 2 × 573 × 0.2 ≈ 230 px。这与测试者"跟不上速度"一致。

机器人之所以能拿 99%，是因为它每 15 ms 直接读真实坐标，相当于"零延迟 + 完美预测"。所以机器人的 Tracking 分数不能用来评估人类难度。

### 4.2 新页面第一次点击时 `new AudioContext()` 同步阻塞约 220 ms（中等）

- 现象：每个新开的页面，第一次点 "Click to play" 后会出现一段 150–242 ms 的帧间隔，而 rAF 内 JS 只有约 0.1 ms。在 6 个新页面里出现了 5 次：冒烟局 150 ms、B 183 ms、B′ 175 ms、C 200 ms、诊断局 242 ms；A 组首局只有 25.9 ms
- 根因（Chrome trace 实测）：`pointerdown` 捕获监听器 → `audio.unlock()`（`src/game/mount.ts:307` → `src/audio/synth.ts:17`）→ `AudioContext::AudioContext` → `RendererWebAudioDeviceImpl` → **`AudioOutputDevice::GetOutputDeviceInfo` 同步阻塞 218 ms**，整个 RunTask 223 ms
- 影响：卡在倒计时 "3" 刚出现的时候，不在计分阶段内，但展位上每次刷新页面后第一位玩家都会遇到。注意测试时带了 `--mute-audio`；不静音时这一步的耗时可能不同，未单独测

### 4.3 每次加载有 2 条 `/favicon.ico` 404（轻微）

`index.html` 没有 `<link rel="icon">`，`vite preview` 对 `/favicon.ico` 返回 404，每次加载有 2 条 `Failed to load resource`。console message 的 location 已确认就是 `http://localhost:5201/favicon.ico`。页面自己发出的请求全部 200。

### 4.4 每次加载有 8 条 three.js 警告（轻微）

警告内容为 `THREE.Material: parameter 'blending' has value of undefined.`，来自 `src/render/fx.ts:31` 的 `flat()`：非 additive 时传了 `blending: undefined`。功能不受影响，但会污染展位排障时看的控制台。

### 4.5 无法覆盖的部分

- 自适应降分辨率（`adaptQuality`）在这台机器上从未触发，降档路径没有被真机验证，建议在弱 GPU 上测
- JS 耗时不包含 GPU 执行时间。不过 120 Hz 下关卡内 0 帧超过 1.5× 周期，说明 GPU 每帧都在 8.3 ms 内完成
- 人工试玩时运营面板的 fps / p95：测试者跳过，未读到
- INITIALS 输入流程：机器人按任务书始终走空闲超时，没有覆盖

| 7 | 有没有卡顿、闪屏、画面错位或其他 bug？各局得分？ | “bug倒是没有”。各局得分：跳过 |
| — | 运营面板 fps / p95 | 跳过 |
| — | 附加：窗口是谁拖的 | “跑测的时候是我拖动的，因为挡住我看电脑屏幕了，可以在后台测试吗” |

关于"可以在后台测试吗"，已实测：无头 Chrome 在这台 Mac 上同样用真 GPU（`ANGLE Metal Renderer: Apple M2 Pro`），但 rAF 由固定 60 Hz 的内部定时器驱动（实测每帧 16.7 ms，与屏幕无关），测不了 120 Hz 和显示端的掉帧。因此 `bot_mbp.py` 加了 `--headless` 开关，只建议用于耐久、内存、报错和 JS 耗时类测试；帧率和掉帧仍要用有头窗口实测，并且跑测时不要动窗口。

## 6. 调参与修复建议（只是建议，本分支没有改任何游戏代码）

按优先级排列：

1. **彗星难度**（对应 §4.1，影响最大，也最可能是"无趣"的直接来源：挫败感读起来就是无聊）。下面几条可以组合使用：
   - 去掉瞬时反向，或者改成约 400 ms 的减速-掉头过渡；反向间隔从 1.5–3 s 拉长到 4–6 s
   - 振幅整体乘 0.6：模拟得到速度 p50 342 px/s、p90 647 px/s、max 958 px/s。乘 0.7 时为 p50 399、p90 755、max 1,117 px/s
   - halo 半径 46 → 60–64 px，并加滞回：出圈超过约 120 ms 或离开 1.25R 才算断锁
   - 速度随时间爬坡：开头 50%，20 s 内逐步升到 100%，前几秒让人先"抓住"
   - 锁定奖励从连续 3 s 降到 2 s，或者改为"5 s 窗口内累计 3 s"
   - 调完后用人测，不要用机器人：机器人在任何参数下都会接近 100%
2. **首次点击卡顿**（对应 §4.2）：在 `mountGame()` 时就创建 `AudioContext`。不需要用户手势，创建出来是 suspended 状态。`unlock()` 只负责 `resume()`，这样约 200 ms 的设备查询就挪到加载阶段，不落在交互上。也可以放到 ATTRACT 的 `requestIdleCallback` 里
3. **趣味性**（测试者 0 分）。样本只有 1 人，以下是测试方的观察，仅供参考：
   - 闪电段：5 次试验每次随机等 1.2–3 s，整段约 10.7–12.3 s，大部分时间在看静止的天空。可以缩短等待（如 0.8–2 s），加入蓄力暗示（云层变暗、雷声渐强），或者加诱饵闪光
   - 无人机段：20 s 内是同一种目标逐个出现。可以加变化，比如移动的无人机、同时出现两架、连击越高窗口越短
   - 结果反馈：每局的分数构成和"差多少能上榜"可以更显眼；连击时加升调音效等成长感
4. **控制台清洁**（对应 §4.3 / §4.4）：加 `<link rel="icon" href="data:,">` 或一个程序生成的 SVG favicon；`flat()` 非 additive 时传 `NormalBlending` 或者不传这个键
5. 可选：这台机器 DPR 2 下 GPU 余量很大，可以考虑在 `adaptQuality` 有余量时把渲染倍率上限从 1.5 放到 2，让 Retina 更清晰；现有的降档逻辑可以兜底

## 7. 复现

```bash
python3 -m venv /tmp/pwenv && /tmp/pwenv/bin/pip install playwright   # 仓库外
npm ci && npm run build && npm run preview &                          # :5201
/tmp/pwenv/bin/python playtest/bot_mbp.py --group all --out /tmp/skybreak-run   # 有头，约 20 分钟，期间不要碰或拖动窗口
/tmp/pwenv/bin/python playtest/bot_mbp.py --group soak --headless --out /tmp/skybreak-soak   # 后台耐久（帧节奏是合成的 60 Hz）
```

每组输出 `<group>.json`（汇总）和 `<group>-frames.json`（逐帧原始数据）。本仓库只提交了汇总 JSON 和 `bot-log.txt`（机器人运行日志，北京时间），逐帧数据未提交。
